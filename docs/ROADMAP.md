# Roadmap

This file is the plan of system-stack. The Status page of the site reads it, and the tracker of the project mirrors it.

| ID | Item | Status | Summary |
| --- | --- | --- | --- |
| R1 | The core: parts, needs and the parts that work | done | `@mark1russell7/system-stack` has the format `stack/1`: each part of a system is a record with its needs. `working` gives the parts that work when some parts are down, and `stopped` gives the parts that stop. `checkStack` finds an unknown part, a duplicate id and parts that need each other. `pathSets`, `stopSets` and `smallestStop` give the paths of a part and the sets of parts whose failure stops it. The core names no topic. |
| R2 | The spend add-on: a hard limit for each cost | in progress | `@mark1russell7/stack-spend` has the format `spend/1`: the plan, the price and the limits of the cost of each part. The gate `checkSpend` fails when a cost can grow with no hard limit. An alert is not a limit. `ownerSteps` gives the work of the owner of an account. A record can give the end of a plan: a trial, a free credit or a term. The gate gives a warning before the date, and it fails when the cost after the end has no hard limit. `endStops` gives the parts that stop with a service. `useStates` gives the used amount of each service in a month, from reads: the larger of the count of the stack and the amount of the provider, with levels at 50, 80 and 100 percent of the hard limit. The gate `checkUse` fails when a limit did not hold. The next step is a reader of the usage of each provider, which makes the reads. |
| R3 | The risk add-on: a goal for each function | in progress | `@mark1russell7/stack-risk` has the format `risk/1`: a goal tells how many failures a part must survive, and the smallest chance that it works. Each risk is a query over the records. The gate `checkRisk` fails for each set of parts whose failure stops a part, unless a record accepts the set with a reason and a last date. `goalStates` gives the single points of failure when some parts are down. `worksChance` gives the exact chance that a part works, and the importance of each part. The next step is a read of the parts that are down from the monitors of a system. |
| R4 | The OpenTofu add-on | in progress | `@mark1russell7/stack-tofu` has the format `tofu/1`: the resources of each part, their providers and the variables. `generateTofu` writes one file in the JSON form of OpenTofu, with the sequence of the resources from the needs of the stack. The gate `checkTofu` fails when the planned cost of an account has no hard limit, or is more than it. A layer with an error gives no file. The gate `checkPlan` reads the plan of OpenTofu: it fails for a delete of a resource that must stay, and for a change that no record has. The next steps are a group of resources as one record, for a new copy of a host, and the setup inside a server. |
| R5 | Feeds and a freshness gate | open | A feed reads the facts of a part from its source. A feed of secrets reads only their names. A gate fails when a record is older than its source permits. |
| R6 | A demo on the site | open | The site shows the sample stack. A person puts parts down, and the page shows which functions still work and the cost limit of each account. |
| R7 | One contract for the layers of add-ons | done | Each add-on reads, checks and joins its layer through one shared contract, the entry `@mark1russell7/coeval/layers`. `checkStackLayers` of the core gives the faults of the core and of each layer. `joinStacks` joins the stack documents of some owners into one stack: the core joins the parts, and each add-on joins its layer. A part or a record of two owners is an error, so no document replaces a record of a different owner. Each add-on package gives its add-on in its entry `/add-on`. |
