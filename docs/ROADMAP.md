# Roadmap

This file is the plan of system-stack. The Status page of the site reads it, and the tracker of the project mirrors it.

| ID | Item | Status | Summary |
| --- | --- | --- | --- |
| R1 | The core: parts, needs and the parts that work | done | `@mark1russell7/system-stack` has the format `stack/1`: each part of a system is a record with its needs. `working` gives the parts that work when some parts are down, and `stopped` gives the parts that stop. `checkStack` finds an unknown part, a duplicate id and parts that need each other. `pathSets`, `stopSets` and `smallestStop` give the paths of a part and the sets of parts whose failure stops it. The core names no topic. |
| R2 | The spend add-on: a hard limit for each cost | in progress | `@mark1russell7/stack-spend` has the format `spend/1`: the plan, the price and the limits of the cost of each part. The gate `checkSpend` fails when a cost can grow with no hard limit. An alert is not a limit. `ownerSteps` gives the work of the owner of an account. A record can give the end of a plan: a trial, a free credit or a term. The gate gives a warning before the date, and it fails when the cost after the end has no hard limit. `endStops` gives the parts that stop with a service. `useStates` gives the used amount of each service in a month, from reads: the larger of the count of the stack and the amount of the provider, with levels at 50, 80 and 100 percent of the hard limit. The gate `checkUse` fails when a limit did not hold. The next step is a reader of the usage of each provider, which makes the reads. |
| R3 | The risk add-on: a goal for each function | in progress | `@mark1russell7/stack-risk` has the format `risk/1`: a goal tells how many failures a part must survive, and the smallest chance that it works. Each risk is a query over the records. The gate `checkRisk` fails for each set of parts whose failure stops a part, unless a record accepts the set with a reason and a last date. `goalStates` gives the single points of failure when some parts are down. `worksChance` gives the exact chance that a part works, and the importance of each part. The next step is a read of the parts that are down from the monitors of a system. |
| R4 | The OpenTofu add-on | in progress | `@mark1russell7/stack-tofu` has the format `tofu/1`: the resources of each part, their providers and the variables. `generateTofu` writes one file in the JSON form of OpenTofu, with the sequence of the resources from the needs of the stack. The gate `checkTofu` fails when the planned cost of an account has no hard limit, or is more than it. A layer with an error gives no file. The gate `checkPlan` reads the plan of OpenTofu: it fails for a delete of a resource that must stay, and for a change that no record has. A group is one record for the resources of a host, and each copy of it makes those resources for one part. The setup inside a server is R9. |
| R5 | Feeds and a freshness gate | in progress | `@mark1russell7/stack-feeds` has the format `feed/1`: each feed lists the parts of some kinds from one source, with the largest age of its newest read. A read has only names, so a feed of secrets reads only their names. The gate `checkFeeds` fails for a name with no part, for a part that its source does not show, and for a feed with no read or an old read. An ignore record has a reason and a last date. The next step is the programs that read each source. |
| R6 | A demo on the site | done | The home page shows the sample stack as a graph from the layout engine `ireko`. A person selects a part or a scenario to put parts down. Then the page shows which parts still work, the single points of failure of the alert, its chance against its goal, and the cost limit of each account. A stop by code holds only while its part works (`stack-spend` 0.1.12). Each answer comes from a query of the packages. The model of the page has no DOM code, and its tests run in Node.js. |
| R7 | One contract for the layers of add-ons | done | Each add-on reads, checks and joins its layer through one shared contract, the entry `@mark1russell7/coeval/layers`. `checkStackLayers` of the core gives the faults of the core and of each layer. `joinStacks` joins the stack documents of some owners into one stack: the core joins the parts, and each add-on joins its layer. A part or a record of two owners is an error, so no document replaces a record of a different owner. Each add-on package gives its add-on in its entry `/add-on`. |
| R8 | The placement add-on: placement as a query | in progress | `@mark1russell7/stack-placement` has the format `placement/1`: the candidates of each slot and the shared parts. `planPlacement` gives the front of the expected cost against the chance from `worksChance`. Nobody picks a placement by hand. Next: candidates from live offers. |
| R9 | The setup add-on: the setup inside a host | done | `@mark1russell7/stack-setup` has the format `setup/1`: the variables and the profiles of the hosts, each with typed steps. `setupScript` writes a POSIX shell script for one host, with the profiles in the order of the needs. Each step checks before it changes, so a second run shows no change. The mode `check` changes nothing, and it exits with 2 when a step has a change. The script reads each variable from its environment, so it holds no secret. The gate `checkSetup` fails for a secret that each user can read, for two steps that write one path, and for a cycle. A CI job starts the script two times on a runner. Version 0.1.0 is on npm since 2026-11-21. |
| R10 | The endurance add-on: stores, draws and converters | in progress | `@mark1russell7/stack-endurance` has the format `endurance/1`: resources, stores with due dates, draws with a level and a supply part, direct uses, converters, cases with survival curves of their cuts, and yearly priors. `enduranceOf` gives the days that each draw holds when a case cuts its supply, and the resources that are used up then. `yearShortfall` gives the user-days of each level in one year. In 0.1.1, a horizon counts only the first days of each cut, for a target of a buy plan. In 0.2.0, each higher draw keeps back its own days of demand, a year counts the expected events, and a stop through the stack has two curves. `levels` takes one event, and `upper` is a limit for each dependence of the cuts. Only the cuts that can reach a supply count. The gate `checkEndurance` examines the layer. In 0.3.0, a converter can give a resource, so chains of converters work, and the gate refuses a cycle. In 0.3.2, `independent` gives the shortfall when the cuts are independent. In 0.4.0, a cut can have no curve yet, and the draws that it can stop are no read. The workflow `bench.yml` measures the cost of the independent stop at 4, 8 and 12 cuts in CI, against frozen limits. In 0.5.0, the minimal stop sets come from the structure of the needs (`stopSets` with `among`, system-stack 0.1.8), so a case with more than 12 cuts keeps an exact `upper`. In 0.6.0, `independent` is exact past 12 cuts too, through the Shannon expansion of `pathSetReliability` (collections), in a budget of work. The next step is the best share of the stores. |
| R11 | The hazard data: the cuts of each hazard case | in progress | `@mark1russell7/stack-hazards` has the format `hazards/1`: reference parts for the public supplies, hazard cases with generic names, the cuts that public pages name, and a source with a license for each claim. `hazardCase` gives the values of `CaseCuts` for a stack and a region. A supply with no cut is no read. The gate `checkHazards` refuses a law with no source or no license, and a law of one chosen region. `outageReader` reads county outage records, and `outageCurves` gives the Kaplan-Meier curve of each region. The workflow `hazards-fit` makes the curves of each state from EAGLE-I (CC BY 4.0) in CI. The grid cut of a power outage has the law of EAGLE-I, with a curve for each state. The grid cut of each storm case has a law from the outages of EAGLE-I in the storm events of NOAA. The next step is the first release on npm. |
